Quality red flags left by the earlier AI work

  • God classes: AuthorityManager 1668 lines (leagues, cups, prizes, seasons, messages), MatchEngineDebugScreen 1324, JobManager 1117, MainMenuManager 1081.
  • Two match-result paths, each creating its own simulator. Two SquadScreenTable classes.
  • Three logging styles (585 System.out, 330 Gdx.app.log, 362 DebugLogManager). About 60 "CRITICAL FIX" comments.
  • About 3.5k lines of dead 3D demo code plus unused bullet/box2d deps and PDFs inside resources/ (the PDFs are what breaks Maven 3.9 filtering).
  • 63 markdown files in the repo root (25k lines, all written 14–21 Dec 2025), several outdated or contradicting the code.
  • Static singletons (DatabaseLoader) causing test-order problems, the same issue as the 2023 Jenkins commits.

Match engine: documents vs reality

Option in the docsClaimed effortReality check
A. Statistical result generatorabout 3 weeksexists as MatchSimulator, but strength barely matters (random ±30% swamps the 0.4/0.6 thresholds)
B. Event / possession text engine2–3, 4–6 or 8 weeks (same phase, different docs)Not started. Needs lineups and positions, which the data model lacks
C. 2D physics simulation (22 players, Box2D)5–12 weeks; "$60K"Prototype: 2 players + ball, debug screen only. Too slow to simulate a whole league every day
D. DarkBlade port16 weeksIn practice "use Ashley + Box2D + gdx-ai", which Futtoboru already depends on. Same as C
Historical errors to fix before reusing any design doc. About 12 docs say the offside rule was "2 opponents (changed from 3 in 1888)". In fact the 3-player rule ran 1866–1925. Several docs also list penalty-area fouls (no penalty kick until 1891) and yellow/red cards (1970). None mention that 1888 used one umpire per side plus a referee on the touchline.

Recommended engine shape (option B-lite)

Headless, unit-testable, reproducible from a seed, fast enough to simulate a full matchday instantly. Calibrate it against the real 1888–89 results: the full fixture list is public, and the game doesn't hold it yet. 2D becomes a viewer of the event list, not the source of truth. Estimate: 2–4 weeks of focused work.

Docs, research and marketing

Historical research (futtoboru_cursor_pm)

  • Real data: 1888–89 rosters only. Files 1–12 are identical to what the game already ships. The game's own copies of files 13–35 (cup clubs) are better.
  • Padding: Burnley has 25 of 31 players with a placeholder 1865 birth year, "added to meet minimum 11", some from later seasons. Pat Gallocher is listed at two clubs. These are in the shipped game data too.
  • "1888–2029": 14 decade essays with zero data rows. Several wrong facts (for example Napoli 1989 title, Gillingham founded 1889), and invented "future" history.
  • Keep: season-scripting / "seasons as releases" idea, 1889–90 design, writing guidelines.

Marketing (futtoboru_mkt)

  • "Investor-ready" analysis with 75–522% ROI, "zero competition", "70–80% success probability": invented numbers.
  • Commit messages describe files that were never committed. Dates say 2024/Jan 2025 instead of Dec 2025.
  • Useful later: GitHub growth plan (README polish, Reddit/HN), Reddit/Twitter templates, competitive analysis, "no campaign until matches work" go/no-go rule. These are currently untracked files.
  • ONLINE_PRESENCE_ANALYSIS_2025.md profiles your personal accounts. Keep it private or delete it.
Unmerged branches worth a look. feature/competition-completion-v1 (Jun 2026, fast-forwards on develop) has real fixes: cup completion and runner-up, next season generated when a league ends, null-team guard, 3 tests. It also has junk: a 77 KB UTF-16 temp_develop.java, a duplicated test, 22 more markdown files. cursor/startup-fixes-and-logging is obsolete (develop already has the null checks). Every other branch is merged.

Running Futtoboru in parallel on BOOK3PRO

BOOK3PRO is a Windows laptop (12 threads, 11 GB, WSL2) and is already your second darkblade machine. Unlike darkblade's LAN/Bitbucket setup, Futtoboru lives on GitHub, so it works the same from any network.

One-time setup on BOOK3PRO (PowerShell)

# 0. Prereqs: Git for Windows (with Git Credential Manager), Temurin JDK 17, Maven 3.9 (after the filtering fix)
java -version ; mvn -v ; git --version

# 1. Clone the real repo (GitHub works from any network)
git clone https://github.com/Geomancer86/Futtoboru.git C:\git\futtoboru
cd C:\git\futtoboru
git checkout develop
git config user.name  "Nicolas Alvargonzalez"
git config pull.rebase false
git config core.autocrlf true        # until a .gitattributes is committed

# 2. Build & run (works after task P1-1 lands; before that, install Maven 3.6.3)
mvn -DskipTests package
java -jar futtoboru-desktop\target\futtoboru-desktop-0.4.0-SNAPSHOT-jar-with-dependencies.jar

# 3. The formerly local-only docs come with the clone: docs/archive/

# 4. Daily routine on either machine
git fetch origin ; git switch develop ; git pull
git switch -c b3/ENG-02-pick-xi      # ws/... on the workstation
# ... work, commit small slices ...
git fetch origin ; git merge origin/develop ; mvn verify ; git push -u origin HEAD

One-time setup on WORKSTATION (before BOOK3PRO starts)

  • Make one canonical checkout. The quickest: in G:\git\futtoboru run git switch develop && git pull (fast-forwards 155 commits; no local work is lost because the current branch has no commits of its own). Then treat futtoboru_cursor\ as a read-only archive.
  • Push the v0.4.0 release so main on GitHub stops showing 2023: git push origin main from the futtoboru_cursor copy (you run this; agents don't push to main).
  • Commit a short CLAUDE.md + docs/HANDOFF.md to develop so both machines' Claude sessions follow the same rules (fetch first, claim item, never force, no push to main).
  • For parallel agents on one machine, use git worktree add .worktrees/<item> -b ws/<item> origin/develop. This is the same model as darkblade.
  • gh CLI isn't installed on the workstation; install it (winget install GitHub.cli) if you want agents to open PRs and create the private archive repo.
